# Scholion — Project Structure & Development Workflow

This document explains how the repository is organised, how the two platform
builds relate to each other, and how to make changes without breaking the
automation or the file structure. It is intended as a reference for the
developer (or any future contributor) rather than as a public-facing overview.

---

## Repository Layout

```
Scholion/                          ← git repo root
  scholion/                        ← macOS build + ALL shared source
    src/                           ← shared .cpp files (compiles on all platforms)
    include/                       ← shared headers
    resources/                     ← AppIcon.icns, Info.plist
    scripts/
      make_icon.py                 ← generates .icns (macOS) AND .ico (Windows)
    third_party/                   ← imgui, mupdf, tinyfiledialogs
    build/                         ← CMake output; Scholion.app lives here
    CMakeLists.txt                 ← macOS build system
    CLAUDE.md                      ← AI assistant instructions for this tree
    docs/                          ← this file and other developer docs
  scholion-win/                    ← Windows build tree (NO duplicate source)
    src/
      platform_win.cpp             ← Windows-only init stub
    resources/
      AppIcon.ico                  ← auto-generated by make_icon.py
      scholion.rc                  ← Windows resource file (icon + version)
      Scholion.manifest            ← DPI awareness (PerMonitorV2)
    third_party/
      glad/                        ← OpenGL 3.3 Core loader (generated)
      mupdf/lib/                   ← Windows .lib files (not in repo; see note)
    CMakeLists.txt                 ← Windows build system
    setup_windows.ps1              ← one-script MSYS2 + dependency bootstrap
    CLAUDE.md                      ← AI assistant instructions for this tree
```

The critical point: **`scholion/src/` and `scholion/include/` are the single
source of truth for all application logic.** The Windows CMakeLists points
directly at `../scholion/src/` — there are no copies. Platform-specific
behaviour is handled entirely by preprocessor guards inside those shared files.

---

## Platform Guards

```cpp
#ifdef __APPLE__
    // macOS-only code (Cocoa file handlers, ICNS, fork/execl, etc.)
#elif defined(_WIN32)
    // Windows-only code (GLAD, DWM, ShellExecuteW, SHGetKnownFolderPath, etc.)
#else
    // Linux stub (future)
#endif
```

Any feature that needs platform-specific behaviour goes into the shared file
with these guards. Only code large enough to warrant its own translation unit
(e.g. a substantial subsystem) goes into `platform_win.cpp`.

---

## How a Change Flows to Both Apps

1. **Edit** `scholion/src/*.cpp` or `scholion/include/*.h`.
2. **Build macOS** to verify: `cd scholion/build && make -j$(sysctl -n hw.ncpu)`.
3. **Commit** the changed files (both `scholion/` and `scholion-win/` paths as
   needed — they are in the same repo).
4. **Push** to the appropriate branch.
5. **GitHub Actions** sees the push and builds both targets from the same
   commit. The macOS workflow compiles from `scholion/`; the Windows workflow
   compiles from `scholion-win/` which pulls shared source via the relative
   `../scholion/src/` path.

One push → both apps rebuilt. No manual sync required.

## Rules for Specific Change Types

| What you're changing | Where it goes | Additional step |
|---|---|---|
| Bug fix / feature (all platforms) | `scholion/src/` or `scholion/include/` | Nothing extra |
| New `.cpp` source file | `scholion/src/` | Add to **both** CMakeLists.txt files |
| macOS-only code | `#ifdef __APPLE__` block in shared file | Add macOS-only lib to `scholion/CMakeLists.txt` if needed |
| Windows-only code (small) | `#ifdef _WIN32` block in shared file | Add Windows-only lib to `scholion-win/CMakeLists.txt` if needed |
| Windows-only code (large) | `scholion-win/src/platform_win.cpp` | Add to `scholion-win/CMakeLists.txt` |
| Icon change | Edit `scholion/scripts/make_icon.py`, then run it | Script auto-writes both `.icns` and `.ico` |
| New Windows system lib | `scholion-win/CMakeLists.txt` → `target_link_libraries` | Nothing extra on macOS side |

## Icon Generation

The icon script is the single source of truth for both platform icons:

```bash
cd scholion
python3 scripts/make_icon.py
```

This produces:
- `scholion/resources/AppIcon.icns` — used by the macOS `.app` bundle
- `scholion-win/resources/AppIcon.ico` — used by the Windows `.exe` via `scholion.rc`
- `scholion/resources/scholion_icon_1024.png` — preview / reference

Run the script and commit both output files any time the icon changes.

## GitHub Actions / CI Automation

- Automated artifact builds run on the **`main` branch only**.
- Pushing to a feature branch (e.g. `feature/text-highlights-references`) is
  safe and does **not** trigger a build or produce downloadable artifacts.
- Merging a feature branch to `main` and pushing triggers both the macOS and
  Windows build workflows.
- Until a feature branch is merged, test locally on macOS via
  `open scholion/build/Scholion.app`. The Windows build must be validated
  manually on a Windows machine (or via the CI artifact after merge).

## MuPDF on Windows

MuPDF `.lib` files are **not** committed to the repo (large binaries). When
setting up a fresh Windows build:

1. Build MuPDF from source matching the bundled headers in `scholion/third_party/mupdf/include/`.
2. Place `libmupdf.lib` and `libmupdf-third.lib` in `scholion-win/third_party/mupdf/lib/`.
3. Pass `-DSCHOLION_WITH_MUPDF=ON` to CMake.

Without these files, the app compiles with stub PDF functions (no PDF loading).

## Key Invariants

- `scholion/src/` is the **only** place application logic is written.
- `scholion-win/` contains **no** `.cpp` files duplicated from `scholion/src/`.
- The icon script is run and **both** output files are committed together.
- Feature branches do not affect CI artifacts — merge to `main` to publish.
- MuPDF `.lib` files are never committed to the repo.
